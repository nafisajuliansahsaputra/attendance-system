# Schedule Materialization & Device API v1

**Status:** implemented foundation  
**Last updated:** 2026-09-03

This document records the concrete runtime behavior that now exists for schedule generation and the first physical-device API stage. It complements `05-DEVICE-PROTOCOL-AND-SIMULATOR.md`.

---

## 1. Schedule materialization

Attendance schedules are configured as reusable rules, then materialized into dated occurrences plus participant snapshots.

The database function is:

```text
materialize_attendance_schedule_range(institution_id, start_date, end_date)
```

A second helper materializes only the institution-local school date containing one device timestamp:

```text
materialize_attendance_schedule_at(institution_id, occurred_at)
```

### Why materialization is required

Reports cannot infer absence from scans alone. If nobody scans on a required school day, that day must still exist as a concrete occurrence with required participants so the homeroom workflow can show Pending and later Sakit/Izin/Alpa.

For this reason materialization is triggered from:

- the physical device card-scan path for the current school date;
- the homeroom daily snapshot before it is read;
- the class report path for the requested date range.

### Idempotency

A source schedule rule can create at most one occurrence for a given school date:

```text
(source_schedule_rule_id, school_date)
```

Repeated materialization is safe and does not duplicate participant rows.

### Participant snapshot

Participants are resolved from historical enrollment on the occurrence date. Supported targets are:

- `ALL_STUDENTS`
- `GRADE_LEVELS`
- `CLASSES`
- `DEPARTMENTS`
- `SELECTED_STUDENTS`

The resulting `session_participants` rows preserve who was expected to attend that concrete occurrence.

### Special-date relationships

- `NORMAL` — ordinary schedule.
- `ADDITIVE` — coexists with normal sessions.
- `REPLACE_NORMAL` — cancels normal occurrences on the same school date.
- `CANCEL_NORMAL` — cancels normal occurrences without creating required participants for itself.

If canonical attendance already exists on a normal occurrence, a later replace/cancel operation fails closed with `SCHEDULE_OVERRIDE_CONFLICT_WITH_ATTENDANCE` rather than rewriting historical truth.

### Supported recurrence subset

The current parser intentionally supports only:

```text
FREQ=DAILY
FREQ=WEEKLY
BYDAY=MO,TU,WE,TH,FR,SA,SU   # WEEKLY only
INTERVAL=N
```

A null/blank recurrence is a one-off occurrence on `starts_on`.

Unknown RRULE properties, unsupported frequencies, malformed intervals, or unsupported combinations fail explicitly. The application must not silently interpret only part of a recurrence rule.

## 2. Device credential model

Physical terminals and local bridges never use staff/admin credentials.

Each active device has:

- device UUID;
- protocol version;
- server-issued random secret;
- only a SHA-256 hash of that secret stored in the database.

The plaintext secret is generated by the provisioning script and printed once:

```bash
npm run device:rotate-secret:env
```

Required provisioning environment:

```text
SUPABASE_URL
SUPABASE_SECRET_KEY
DEVICE_ID
```

The generated secret uses the form:

```text
ats_dev_<random base64url bytes>
```

The database stores only:

```text
sha256:<64 lowercase hex characters>
```

Rotating a secret invalidates the previous one immediately. A revoked device cannot receive a new secret through the rotation RPC.

## 3. Device API v1 headers

Every implemented device endpoint requires:

```http
Authorization: Bearer <device-secret>
X-Device-Id: <device-uuid>
X-Protocol-Version: v1
```

Authentication validates all three values against the active device record. Failure returns a generic authorization error and does not reveal which credential field was wrong.

Network deployment requires HTTPS.

## 4. Heartbeat

Implemented endpoint:

```text
POST /api/device/v1/heartbeat
```

The endpoint authenticates the device and refreshes `last_seen_at`.

Successful response shape:

```json
{
  "ok": true,
  "deviceId": "...",
  "protocolVersion": "v1",
  "serverTime": "2026-09-03T12:00:00.000Z"
}
```

No student, staff, class, or institution administration data is returned.

## 5. Card scan — Stage 1

Implemented endpoint:

```text
POST /api/device/v1/card-scan
```

Request body:

```json
{
  "requestId": "device-generated-idempotency-key",
  "rfidUid": "A4:B8:32:F1",
  "occurredAt": "2026-09-03T06:45:00+07:00"
}
```

The device does **not** send authoritative student, class, institution, session, or late-status values.

Server flow:

```text
authenticate device
  -> validate timestamp / replay window
  -> materialize institution-local schedule date
  -> resolve RFID owner + historical enrollment
  -> resolve candidate session + eligibility + duplicate state
  -> decide stage-one outcome
```

Current clock tolerance:

- up to 10 minutes old, supporting short network retries;
- up to 2 minutes in the future, tolerating limited device clock skew.

Older/future events are rejected instead of being allowed to manipulate lateness.

### Stage-one outcomes

```text
CAPTURE_FACE
ACCEPT_WITHOUT_FACE
UNKNOWN_CARD
NO_ACTIVE_SESSION
NOT_ELIGIBLE
DUPLICATE_ATTENDANCE
FACE_PROFILE_MISSING
```

Ambiguous overlapping sessions fail closed as a configuration/system error.

## 6. Face-required sessions

When the resolved session requires face verification, Stage 1 creates a short-lived opaque verification transaction bound to:

- institution;
- authenticated device;
- request ID;
- expected RFID owner;
- concrete occurrence;
- active face profile;
- RFID UID;
- scan timestamp.

Response:

```json
{
  "requestId": "...",
  "code": "CAPTURE_FACE",
  "verificationTransactionId": "...",
  "expiresAt": "..."
}
```

The transaction expires at the earlier of:

- two minutes after creation; or
- the attendance session closing time.

Reusing the same request ID with changed identity/session bindings is rejected.

**Stage 2 face sample upload/verification is not implemented yet.** It will be added only after the real 1:1 face-verification model, threshold calibration, sample transport, and retention policy are locked.

---

## 7. Sessions without face requirement

A session may explicitly have `face_verification_required = false`.

In that case the server does not call a fake verifier and does not record `MATCH`. Instead the canonical attendance engine receives:

```text
face.status = not_required
```

Persistence records:

```text
verification_result = NOT_REQUIRED
```

The rest of the canonical attendance rules still apply: registered card, active session, eligibility, duplicate protection, time window, and lateness.

---

## 8. Raw events and privacy

Stage 1 persists machine/audit events separately from canonical attendance. The public API response intentionally avoids student names and other unnecessary profile data.

Direct browser roles (`anon` and `authenticated`) have no table access to device verification transactions. Device and schedule RPCs are service-role-only and invoked from the server application.

## 9. Current implementation boundary

Implemented now:

- recurrence materialization and participant snapshots;
- daily/report materialization hooks;
- device secret rotation;
- device authentication;
- heartbeat;
- Stage 1 RFID card scan;
- short-lived face-verification transaction creation;
- explicit `NOT_REQUIRED` face state;
- raw Stage 1 audit events;
- timestamp/replay tolerance;
- unit coverage for stage resolution and credential parsing.

Not implemented yet:

- Stage 2 face sample transport;
- real face service/model;
- physical serial bridge;
- ESP32/Arduino firmware;
- network rate limiter / deployment-edge protections;
- full physical-device end-to-end test using a provisioned plaintext device secret.
